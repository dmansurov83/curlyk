# Фича: многострочный синтаксис запроса (continuation-строки URL)

## Цель

Поддержать разбиение длинного запроса на несколько строк: после request-строки
(`METHOD URL`) допустимы строки с отступом, которые **конкатенируются** в единый
URL без пробелов. Это делает длинные URL и query-параметры удобочитаемыми.

```
GET http://example.com:8080
    /api
    /html
    /get
    ?id=123
    &value=content
```

дает `http://example.com:8080/api/html/get?id=123&value=content`.

Перенос строки внутри request-блока пользователь делает в многострочном теле или
вставкой текста; на request-строке Enter по-прежнему открывает меню действия
(отдельная клавиша переноса не вводится: Shift+Enter неотличим от Enter в
текущем стеке ввода bubbletea v1.3.10 / coninput на Windows).

## Дизайн

- Склейку делаем **в парсере** (`ParseFile`): сразу после request-строки, пока
  `mode == modeHeaders`, любые строки с ненулевым отступом (ведущие пробелы или
  табы) и НЕ похожие на заголовок (`Name:`), опцию (`@...`) или комментарий —
  добавляются к URL текущего запроса (обрезка отступа, без добавления пробела).
  Непустая строка без отступа завершает URL-континуацию и обрабатывается обычным
  образом (заголовок/тело/разделитель). Континуация допустима только с отступом.
- В `Request` добавить поле `URLEnd int` (1-based строка последней строки URL,
  по умолчанию `Line`), чтобы редактор/геометрия точно знали, где заканчивается
  request-блок для такого случая, как Enter на строке URL.
- Лексер: продолжать выдавать `TokURL` для континуационных строк (каждая —
  отдельный `TokURL` токен), т.е. в `Lex` в header-режиме строка с отступом без
  параметра `:` классифицируется как `TokURL` (а не падает в тело). Так
  подсветка красит всю многострочную URL как url.
- Токен континуации используется только для подсветки; склейка URL остаётся
  только в парсере, чтобы не было расхождения приложения между лексером и
  парсером.

## Многострочное urlencoded-тело

- Аналогичная континуация поддерживается для тела `application/x-www-form-urlencoded`:
  после пустой строки (начало тела), если Content-Type запроса — urlencoded, строки
  с отступом (`key1 = value1`, `& key2 = value2`, каждая со своим отступом)
  склеиваются в единый urlencoded-образец без переносов и лишних пробелов.
- Распознавание включает анализ заголовка `Content-Type` (поиск подстроки
  `application/x-www-form-urlencoded` в `cur.Headers`) — при другом Content-Type
  тело остаётся сырым, как сейчас.
- Склейка выполняется в парсере (`ParseFile`), в body-режиме, по тем же правилам
  отступа, что и для URL. Нормализуется разделитель: строки, начинающиеся с `&`,
  примыкают к предыдущему значению без лишнего пробела:
  `key1=value1&key2=value2&key3=value3`. Опциональные пробелы вокруг `=` и `&`
  (классическая нотация `key1 = value1`) убираются.
- Модели достаточно поля `Request.Body` (склейка кладётся туда же); отдельное поле
  для конца тела не требуется — существующих `BodyStart`/`BodyEnd` хватает.

**Ключевое условие безопасности:** строка континуации распознаётся ТОЛЬКО по
отступу, пока `mode == modeHeaders`. Мешающих случаев нет: заголовок требует `Name:`,
опция — `@`, комментарий — `#`/`//`. Строка с отступом без `:` в заголовочной
зоне до сих пор считалась телом; после фичи она станет частью URL — это
желаемое поведение и риск ложно не затронет существующие файлы без отступов.
